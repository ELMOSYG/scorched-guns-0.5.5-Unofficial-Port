# 已知问题与已评估方案

这份文件记录**已知但尚未修**的问题，以及每个问题评估过的方案与取舍。
修掉一条就删一条，别让它变成第二个 HANDOFF。

---

## 1. 枪械在铁砧修复会越修越贵，直到"过于昂贵！"修不了

**影响**：高。枪械只有铁砧这一条修复路径（`GunItem.isValidRepairItem`），
而原版铁砧每次操作都会给物品的 `REPAIR_COST` 组件 +2，花费按 2^n 量级上涨。
修几次之后超过 39 级，铁砧直接拒绝——**枪就永久废了**。这个对可玩性影响很大。

**机制**（原版对所有可修复物品都这样，不是本 mod 引入的）：

```
铁砧操作一次（修复 / 合并 / 改名）⇒ REPAIR_COST += 2
花费 ≈ 2^REPAIR_COST 量级 ⇒ 超过 39 级显示 "Too Expensive!"
```

**已评估的三种方案：**

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A（推荐）** | 每 40 tick（2 秒）扫一遍玩家背包，把 `GunItem` 的 `REPAIR_COST` 移除 | 每 tick 约 40 ns（37 格 × 1/40） ⇒ 占 tick **0.0001%**，spark 采不到 | 改动最小、无 mixin、不碰原版逻辑 |
| **B** | `AnvilUpdateEvent` 里自己算修复结果并清惩罚 | 空闲零成本，但要复刻原版修复数学（材料修复量 `maxDamage/4`、合并、改名，约 60 行） | 容易与原版有细微差异 |
| **C** | 独立维修配方（枪 + `repair_kit` ⇒ 修好的枪） | 低 | 绕过经验成本，属于平衡改动 |

**A 的实现细节**（已确认过的取舍）：
- 只在**服务端**跑，客户端零成本；
- 先 `has(DataComponents.REPAIR_COST)` 再 `remove`，99.9% 的调用只做一次查表、不产生修改、不触发同步；
- 只处理 `GunItem`，其它物品的惩罚照旧；
- 建议加配置 `removeGunAnvilPenalty`，默认 `true`。

**为什么值得做**：这不是"数值偏高"，而是**一件装备会永久失去修复能力**——
玩家攒了几十小时的枪因为修了五次就废掉，是最典型的那种"劝退型"设计缺陷。

## 2. 机瞄相机骨骼会有固定偏移

**影响**：中（只影响用了相机骨骼的枪；原版 141 把不受影响）。

1.20.1 的 `GUN_DEFAULT_ORIGIN` 与移植版不同（字节码里能看到 `8.0` 常量），
而 `getCameraBone` 用的是写死的常量，加上骨骼分支绕过了原路径的补偿
（`+0.6059` 等），叠加起来表现为"相机比机瞄低约 2 格"。

**方案**：把骨骼分支**降级为兜底**（有 `ironSight.camera` 数据时优先用数据），
这样已发布行为完全不变；自定义枪改用数据键定位。

## 3. Create 动力合成与枪械工作台的材料不一致

**影响**：中（有 Create 的整合包里能绕过蓝图与部分材料）。

实测：137 把枪两套配方都有，其中 **90 把不一致**——22 把缺蓝图（古典/边疆可接受），
87 把材料不同，其中 78 把是"动力合成少料"（缺枪管、框架、木板、等级金属）。

**状态**：**暂不修**。用户判断"AI 生成配方布局精确度不够"，应由人工改。
需要时用只读脚本输出"哪把枪少了什么"的清单即可。
